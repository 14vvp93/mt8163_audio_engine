# Repository structure and organization

This document defines where project code, research evidence, firmware inputs, generated outputs, and maintenance scripts belong. It is the canonical placement guide for future changes.

## Top-level map

| Path | Purpose | Policy |
|---|---|---|
| `.github/workflows/` | CI, static analysis, archive processing, host tests and build jobs | Keep reproducible workflows; consolidate only after comparing triggers and outputs. |
| `android-test/` | Android-side probes and bring-up utilities | Test-only; never treat as production system components. |
| `cd3313-emulator/` | Host-side CD3313 protocol/register/state model | Keep independent of kernel code; share evidence through docs and tests. |
| `docs/` | Architecture, reverse-engineering evidence, audits and status | Markdown only where practical; link from `docs/README.md`. |
| `kernel/cd3313/` | CD3313 kernel-driver rewrite | Target-kernel code and driver-specific tests belong here. |
| `pcm-dsp/` | PCM/DSP algorithms, Android effect adapter, tests and benchmarks | Keep algorithms independent from Android-specific adapters. |
| `reference-materials/` | Immutable firmware inputs and curated extracted references | Never modify source evidence in place. |
| `scripts/repository/` | Repeatable repository inventory, extraction and curation scripts | Scripts must be deterministic, safe to rerun and documented. |
| `tools/` | Diagnostic and reverse-engineering utilities | Utilities must state whether they read or modify a device. |

## Reference-materials layout

- `reference-materials/firmware-dumps/` — original firmware dump files and split archive volumes.
- `reference-materials/heq/` — original split HEQ archive volumes.
- `reference-materials/kernel/` — original kernel modules and other kernel reference binaries, where present.
- `reference-materials/extracted/system/` — curated System-side audio policy, libraries and framework artifacts.
- `reference-materials/extracted/vendor/` — curated Vendor-side audio libraries, configuration and kernel modules.
- `reference-materials/extracted/manifest.json` — source archive member, destination, byte size and SHA-256 for every curated file.

The original split archives are retained as source evidence. The full extraction is reproducibly generated by `scripts/repository/prepare_reference_archives.py`; the audio-focused persistent subset is generated by `scripts/repository/curate_audio_references.py`. Do not manually edit generated files under `reference-materials/extracted/`: update the curation rules and rerun the workflow instead.

The complete extraction is intentionally not committed wholesale. It contains unrelated Android files and very large assets. The workflow artifact is temporary; the curated tree and original archive parts are the durable repository sources.

## Naming rules

- Use lowercase kebab-case for new directory and file names, except where an upstream filename must be preserved for ABI or forensic accuracy.
- Preserve original binary names and original directory paths inside firmware reference trees.
- Do not rename a firmware binary merely to make its name prettier: record a human-readable label in the manifest or documentation instead.
- Use descriptive Markdown names in `docs/`, grouped by subsystem prefix (for example `CD3313_` and `MT8163_`).
- Keep one authoritative index at `docs/README.md` and one project entry point at the root `README.md`.

## Generated and temporary content

Do not commit:
- build directories, object files, intermediate shared libraries, temporary unpack directories, caches or test logs;
- duplicate extraction trees that can be regenerated from retained source archives;
- workflow artifacts or downloaded copies of files already tracked with identical hashes.

Commit intentional test fixtures only when they are small, reproducible and necessary for offline tests. Large immutable firmware inputs should remain in their original archive form or be managed as a separately documented artifact.

## Duplicate and deletion policy

1. Compare SHA-256, not filenames, before classifying files as duplicates.
2. Preserve different builds even when basenames match; System, VNDK and Vendor copies may be ABI- or version-distinct.
3. Preserve path context for firmware files when it identifies their original partition or load location.
4. Delete a tracked item only when its redundancy or lack of project value is demonstrated and documented.
5. Keep original archives until every required member has a durable, verified replacement and the deletion decision is recorded.
6. Never delete the only copy of a firmware binary, configuration, source file or test fixture.

## Workflow conventions

- Archive extraction and curation must be reproducible from a clean checkout.
- Validate split-volume continuity, ZIP CRC, path traversal, symlink entries and SHA-256.
- A workflow that writes generated inventory or curated files must target the active working branch explicitly.
- Upload large full-extraction outputs as time-limited artifacts; do not commit them automatically.
- Review workflow triggers for overlapping path filters, duplicate work and stale branch names before removing or consolidating workflows.

## Current known cleanup caveats

- The archive audit reports 1,452 extracted archive members (563.23 MiB uncompressed); this is the full temporary extraction, not the size of the committed curated subset.
- The curated manifest is the authoritative count and byte total for files permanently promoted into Git. Directory entries and the manifest/README are not payload files.
- `files.zip` was removed only after all 36 members were confirmed byte-identical to members in `files2.zip`.
- The split HEQ archive remains retained because its assembled APK is too large for a normal Git blob and remains useful research evidence.
- No other source archive should be removed solely because some extracted files overlap.
