# MT8163 Audio HAL reconstruction

This document records facts recovered from the repository's `files.zip` and the ARM32 Android 9 primary audio HAL. This is static analysis; no head-unit runtime behavior has been assumed.

## Input set

The extracted archive contains 36 files under `files/system` and `files/vendor`, including:
- `vendor/audio.primary.mt8163.so` (ARM32, Android 28, stripped; approximately 1.67 MB);
- `vendor/audio_policy_configuration.xml` and `vendor/audio_policy.conf`;
- `vendor/audio_effects.xml`;
- `vendor/audio_device.xml`;
- `vendor/AudioParamOptions.xml`;
- `vendor/audiocmdservice_atci`;
- MTK audio HIDL service and effect implementation libraries.

## Primary HAL capabilities visible in dynamic symbols

The primary HAL exposes named functions for stream/master volume, external speaker gain, speaker filter parameters, ACF/HCF preview application, ACF/HCF updates, MTK filter lifecycle and PCM processing, filter parameter updates/output gain, and capture/microphone gain and speech routing.

Key symbols include:
- `AudioALSAStreamManager::setSpkFilterParam(unsigned int, unsigned int, int)`
- `AudioALSAStreamManager::UpdateACFHCF(int)`
- `AudioALSAHardware::SetACFPreviewParameter(void*, int)`
- `AudioALSAHardware::SetHCFPreviewParameter(void*, int)`
- `AudioMTKFilterManager::process(void*, unsigned int, void*, unsigned int)`
- `AudioMTKFilterManager::setSpkOutputGain(int, unsigned int)`
- `AudioMTKFilter::setParameter(void*)`
- `AudioMTKFilter::setParameter2Sub(void*)`
- `AudioMTKFilter::setOutputGain(int, unsigned int)`
- `AudioALSAVolumeController::ApplyAudioGain(int, unsigned int, unsigned int)`

These symbols establish that this HAL has an MTK software filter/compensation pipeline and dedicated ACF/HCF parameter paths. They do not, by themselves, prove which filter is active for every Android stream or how this vehicle image configures it. Focused ARM disassembly and call-site analysis are being generated by the [audio HAL analysis workflow](../.github/workflows/analyze-audio-hal.yml).

## Audio effect framework configuration

`vendor/audio_effects.xml` declares AOSP effect libraries: bundle wrapper, reverb wrapper, visualizer, downmix, loudness enhancer, and dynamics processing.

Declared effect types include BassBoost, Virtualizer, Equalizer, Volume, four reverb variants, Visualizer, Downmix, Loudness Enhancer and Dynamics Processing.

The file does not contain active `postprocess` stream chains. Therefore, an effect declaration does not mean it is automatically applied to all music, navigation, Bluetooth or system streams. Our DSP should not depend on ViPERFX or assume these generic effects are globally enabled.

## MTK audio build options

The supplied `AudioParamOptions.xml` identifies platform `MT8163`, speaker path `int_spk_amp`, two microphones, FM support enabled, `MTK_BESLOUDNESS_RUN_WITH_HAL=no`, empty `MTK_ACF_AUTO_GEN_SUPPORT`, and `MTK_AURISYS_FRAMEWORK_SUPPORT=no`.

These are build/configuration options, not runtime measurements. In particular, do not assume BESLoudness is enabled through this build option.

## Audio routing and format configuration

The primary XML module describes 16-bit stereo output at 44.1/48 kHz; primary input at 8/16/32/44.1/48 kHz with mono/stereo and voice-call channel masks; Bluetooth SCO at 8/16 kHz; A2DP stereo 44.1 kHz; USB stereo 44.1 kHz; remote submix stereo 48 kHz; and FM tuner/voice-call endpoints.

The legacy `audio_policy.conf` differs in some details (for example, primary output is listed as 44.1 kHz and PCM 16/32-bit). Both configurations are retained in the archive. Before replacing policy files, determine which configuration Android 9 actually loads on this build.

## Separation: HAL PCM path vs CD3313 control

The HAL's ACF/HCF and MTK filter functions are the natural integration point for PCM DSP. The CD3313 kernel module exposes a separate control device (`/dev/audiomux`) and one-byte I²C register writes. A string scan of `audio.primary.mt8163.so` did not find `audiomux` or `cd3313`; this does not prove that no indirect access exists, but there is currently no evidence that the primary HAL directly calls the CD3313 misc device.

Recommended architecture:
1. Keep Android AudioFlinger/HAL responsible for stream mixing, routing, calls and device lifecycle.
2. Integrate software DSP at the MTK filter/PCM processing boundary, with explicit bypass for call/SCO and unsupported formats.
3. Implement CD3313 control as a separate control service/library using the recovered ioctl ABI; do not conflate register writes with PCM processing.
4. Add stream policy so music, navigation and system sounds can share a tuned output path without breaking call/microphone behavior.
5. Use existing ACF/HCF data structures only after exact layouts and ownership are recovered.
